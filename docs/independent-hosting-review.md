The intended flow (passkey -> account/door/vault keys -> sponsored seat -> bind -> rotating code -> one-shot check-in -> recovery -> Envio history) is substantially represented by code and tests. This is **not** proof of a working production journey. Free sponsored actions are supported; the relayer deliberately does not pay the value for paid listings. `GATE_TOKEN` is optional in API code, but `docs/remaining-work-plan.md` says the browser gate does not send it. Do not put a shared gate secret into the public browser bundle.

On-chain data that persists without old infrastructure includes factory/event registration, ticket ownership and seat state, door binding, listing and check-in history. Off-chain passport ciphertext, any file-based stores, queue/spend/rate/cooldown state, old operational logs and the existing hosted indexer deployment may be lost. The indexer can rederive chain events but cannot recreate missing encrypted passport blobs or private keys.

## 5. Proposed architecture and migration order (approval required)

**Recommendation:** Vercel hosts the existing Vite web build and static assets. Railway runs one persistent `@turnstile/relayer` Node service and a managed Postgres database in the same suitable region. Envio Cloud hosts the existing indexer and Alchemy supplies primary RPC (public Monad testnet RPC for read fallbacks). Railway is recommended over Vercel functions because it has persistent services, service variables, custom domains, health checks, logs, restart behavior and Postgres. Configure **one active writer** for the wallet keys, disable autoscale/parallel replicas and explicitly control overlapping deployments. [Railway pricing](https://railway.com/pricing), [deployment health checks](https://docs.railway.com/deployments/healthchecks) and [Postgres docs](https://docs.railway.com/databases/postgresql). Caveat: Railway startup health checks are not continuous monitoring; add external uptime checks. Render paid always-on web service or a carefully operated VPS are alternatives; free sleeping services and serverless concurrency are not suitable for the relayer.

Proposed sequence, not action already performed:

1. Owner approves target services and independently verifies domain control, hackathon chain requirement, key ownership/funding, current on-chain base URIs and old passport backup availability. Take a non-sensitive inventory and choose production vs staging scopes. No contract edits or transactions.
2. Prepare a minimal repository changeset after approval: Vercel monorepo build settings for `apps/web` (`pnpm` workspace install with frozen lockfile, Node 24, `pnpm --filter @turnstile/web build`, actual `dist` output verified), SPA history fallback, edge redirects from `www` to apex, and `/api/*` reverse proxy to the persistent backend **including metadata and SVG**. Preserve the existing framework and routes. Do not proxy third-party RPC credentials through public server output.
3. Provision an isolated Railway backend and Postgres. Apply the existing schema once after backup confirmation; require `DATABASE_URL` so accidental JSON/memory fallback is rejected in production. Configure one process/replica, stable HTTPS backend address (candidate `api.turnstile.work`), restart and external monitoring, logs with no secrets and a safe non-overlapping rollout/drain policy. Reconcile ambiguous in-flight sends/nonces before allowing new writes after restart. If these safety conditions cannot be established, block real traffic rather than treating one configured replica as proof of safety.
4. Provision a new Alchemy testnet application (private server URL and restricted browser URL) and read-only public fallback. Verify account limits and RPC health. Recreate/index from factory block via Envio Cloud; confirm current GraphQL URL and query shape. Do **not** upgrade Envio tooling automatically. The claimed “14 vulnerabilities” are not identified in checked-in docs or verified by an audit in this pass; run a targeted dependency advisory audit and evaluate tooling-only vs runtime exposure and hosted-indexer compatibility before any upgrade.
5. Use a **controlled staging subdomain only with a separate backend, database, credentials/wallets, Envio configuration and distinct origin policy**. Otherwise use local non-production checks and do not create production passkeys on a Vercel preview domain. Keep production passkeys bound to `turnstile.work`; prefer leaving `VITE_RP_ID` unset so the page hostname supplies `turnstile.work`, or set it explicitly only after verifying staging isolation. Validate exact WebAuthn origin on each host.
6. Route browser `/api/*` through the canonical Vercel origin to Railway so the browser remains same-origin. Railway's direct API address is still public: enforce exact production/staging CORS (not wildcard), allowed Host/origin and trusted proxy chain. Calibrate `TRUSTED_PROXY_HOPS` with `/api/ip`, reject forged `X-Forwarded-For`, and review real client-IP rate limiting. Align `PUBLIC_ORIGIN`, `VITE_SITE_URL`, `VITE_API_URL`, frontend links, metadata and canonical redirects. Confirm public metadata/image URLs resolve at the apex before any DNS cutover.
7. Test repository checks, read-only preflight, source maps/static assets, deep links, metadata/SVG, rate/budget/queue behavior and staging recovery. Only with explicit separate permission, funded throwaway **testnet** wallets and a controlled environment run transaction-spending smoke/judge tests; they consume gas and seats. Verify `www` redirects before WebAuthn initializes, including direct page routes and `/api/*`. Run real-device PRF/passkey checks. Resolve `GATE_TOKEN`/browser authorization without shipping a secret in JS; keep check-in restricted until solved.
8. After successful rehearsals and **separate DNS/deployment approval**, configure Vercel apex and `www`, backend hostname and registrar records shown by providers, TLS and redirects. Do not reuse Replit A/TXT records. Maintain old on-chain metadata URL paths. Verify canonical domain and wallet-funded relayer from outside the provider networks. If the old base URI already uses the canonical domain, **do not send a SetBaseURI transaction**. Update it only if read-only chain verification shows a mismatch and owner approves the transaction.
9. Only after production checks update claims, submission copy and monitoring. Rollback: keep the last healthy Vercel build and backend release plus a tested DB backup; stop writes, drain/check pending transactions, then revert both services together. Never roll back DB without checking schema compatibility and passport watermarks. DNS rollback requires explicit owner approval and a working canonical passkey origin; a preview URL cannot replace it.

### Cost estimate and tradeoffs

As of this audit, [Vercel pricing](https://vercel.com/pricing) lists Hobby at $0/month for **personal non-commercial** use and Pro at $20/month plus usage; confirm plan eligibility. [Railway pricing](https://railway.com/pricing) lists Hobby at $5/month minimum usage including $5 resource credit; always-on compute, database, storage, network egress, backups and higher usage may cost more. [Envio pricing](https://docs.envio.dev/docs/HyperIndex/hosted-service-billing) links to current tiers and a free development tier; check whether the project fits and whether that tier is durable enough. Alchemy rates/credits depend on chosen plan and request volume; domain/registrar and wallet gas are additional. **No defensible exact monthly total** is possible without traffic, database size, Envio tier and provider plan choices. A lower-bound illustration is $5/month Railway minimum with eligible Vercel Hobby, before usage, Envio, Alchemy, domain and gas; a Vercel Pro choice adds $20/month before overages.

## 6. Verification and security gate

After approval, install from the repository lockfile using Node >=24 and pnpm 10.26.1; run CI-equivalent `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm vectors:check`, `pnpm build`, and contract `pnpm --filter @turnstile/contracts check` (Foundry installation/checks per `.github/workflows/ci.yml`). Then run indexer checks, server/web builds, preflight for staging and canonical domain, API/asset/metadata/SVG checks, mobile/desktop journeys and external health monitoring. `pnpm smoke` and `judge` send real transactions/burn seats, so require explicit transaction approval before running on testnet. Never run them on mainnet under this plan.

Security review must verify no committed secrets/private keys or secret-bearing logs/screenshots; encrypted passport/DB protection and backups; wallet reserves and sponsorship budget ceilings; nonce safety across restarts; forged proxy header rejection; strict CORS and WebAuthn RP/origin; session/door expiry and replay rejection; resale ownership; per-IP rate limits; error redaction; key rotation/role ownership; and dependency advisories, especially Envio tooling. Do not equate test coverage with a professional contract audit.
